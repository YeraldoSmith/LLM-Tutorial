## 3.1 Числовые форматы: меньше битов — быстрее и компактнее

Число с плавающей точкой состоит из трёх частей: знака, **порядка** (насколько большим или малым может быть число — **диапазон**) и **мантиссы** (сколько значащих цифр — **точность**).

| Формат | Всего битов | Порядок | Мантисса | Максимум | Примерно значащих цифр |
|--------|-------------|---------|----------|----------|------------------------|
| FP32 | 32 | 8 | 23 | 3,4 × 10³⁸ | 7 |
| FP16 | 16 | 5 | 10 | 65504 | 3 |
| BF16 | 16 | 8 | 7 | 3,4 × 10³⁸ | 2–3 |
| FP8 (E4M3) | 8 | 4 | 3 | 448 | 1 |

Вдвое меньше битов — вдвое меньше памяти и передачи данных, а матричные вычисления на GPU обычно вдвое быстрее (H100 выдаёт около 989 TFLOPS в BF16 и около 1979 в FP8). Плата — точность и диапазон. Смоделируем с помощью модуля `struct`:

```python
import struct

def to_fp32(x):
    return struct.unpack("<f", struct.pack("<f", x))[0]

def to_fp16(x):
    try:
        return struct.unpack("<e", struct.pack("<e", x))[0]
    except OverflowError:                  # вне диапазона FP16
        return float("inf")

def to_bf16(x):                            # BF16 — это старшие 16 битов FP32 (с округлением)
    bits = struct.unpack("<I", struct.pack("<f", x))[0]
    bits = (bits + 0x7FFF + ((bits >> 16) & 1)) & 0xFFFF0000
    return struct.unpack("<f", struct.pack("<I", bits))[0]

print(f"{'x':>13} {'FP32':>14} {'FP16':>14} {'BF16':>14}")
for x in (1 / 3, 3.14159265, 1.001, 70000.0, 1e-8):
    print(f"{x:>13.6g} {to_fp32(x):>14.8g} {to_fp16(x):>14.8g} {to_bf16(x):>14.8g}")
```

- **FP16**: точность приличная, но **крошечный диапазон** — больше 65504 превращается в бесконечность, а меньше примерно 6 × 10⁻⁸ — в 0. Очень маленькие градиенты при обучении просто «исчезают».
- **BF16** (формат, придуманный Google для глубокого обучения): 8 битов порядка, как у FP32, значит **тот же диапазон** и никаких переполнений; но всего 7 битов мантиссы, так что точность очень низкая — `1.001` становится `1`.
- Сейчас стандартный выбор для обучения больших моделей — **BF16**.

## 3.2 Обучение со смешанной точностью

Как же при такой низкой точности BF16 вообще что-то обучает? Ключ — **смешанная точность**:

- матричные умножения **прямого и обратного прохода** (почти всё время) идут в BF16 — быстро и экономно;
- **обновление параметров** выполняется над «главными» весами в FP32.

Почему обновлять нужно именно в FP32? Пример: параметр равен 1,0, и на каждом шаге к нему прибавляется крошечное обновление 0,0001:

```python
import struct

def to_bf16(x):
    bits = struct.unpack("<I", struct.pack("<f", x))[0]
    bits = (bits + 0x7FFF + ((bits >> 16) & 1)) & 0xFFFF0000
    return struct.unpack("<f", struct.pack("<I", bits))[0]

w_bf16, w_fp32 = 1.0, 1.0
for step in range(1000):
    w_bf16 = to_bf16(w_bf16 + 0.0001)      # после каждого шага снова сохраняем в BF16
    w_fp32 = w_fp32 + 0.0001
print("параметры только в BF16:", w_bf16)        # застряли на 1.0!
print("главные веса в FP32:    ", round(w_fp32, 4))
```

Около 1,0 наименьший шаг, который может представить BF16, — 2⁻⁷ ≈ 0,0078, поэтому `1.0 + 0.0001` округляется обратно до 1,0 — обновление **полностью теряется**. В конце обучения обновления часто именно такие маленькие, поэтому параметры нужно хранить и обновлять в FP32 (отсюда те 4 байта главных весов в «16 байтах на параметр» из прошлого урока).

**Масштабирование потерь для FP16**: у FP16 есть ещё одна проблема — очень маленькие градиенты обращаются в 0. Решение: умножить потери на большое число (скажем, 65536), отчего градиенты тоже увеличатся, а потом разделить обратно:

```python
import struct

def to_fp16(x):
    return struct.unpack("<e", struct.pack("<e", x))[0]

g = 1e-8                                   # очень маленький градиент
print("сразу в FP16:", to_fp16(g))
scale = 65536
print("умножили на 65536, сохранили в FP16, разделили:", to_fp16(g * scale) / scale)
```

У BF16 диапазон как у FP32, и масштабирование потерь не нужно — главная причина, по которой он вытеснил FP16.

В PyTorch смешанная точность — это один `torch.autocast`:

```python requires=torch timeout=120
import torch

torch.manual_seed(0)
device = "cuda" if torch.cuda.is_available() else "cpu"
model = torch.nn.Sequential(torch.nn.Linear(64, 256), torch.nn.GELU(), torch.nn.Linear(256, 1)).to(device)
opt = torch.optim.AdamW(model.parameters(), lr=1e-3)
x = torch.randn(512, 64, device=device)
y = 2 * x[:, :1] + 0.5

for step in range(201):
    with torch.autocast(device_type=device, dtype=torch.bfloat16):   # матричные операции здесь — в BF16
        pred = model(x)
    loss = torch.nn.functional.mse_loss(pred.float(), y)
    opt.zero_grad()
    loss.backward()
    opt.step()                                                       # параметры и градиенты остаются в FP32
    if step % 50 == 0:
        print(f"step {step:3d}  loss {loss.item():.4f}  выход {pred.dtype}  "
              f"веса {model[0].weight.dtype}  градиенты {model[0].weight.grad.dtype}")
```

**Обучение в FP8**: DeepSeek-V3 (2024) перевела большую часть матричных умножений в FP8, удерживая ошибку «мелкозернистым масштабированием» (свой множитель для каждого небольшого блока данных), и стала одной из первых моделей, успешно обученных в FP8 в очень больших масштабах.

## 3.3 Накопление градиентов

Чем больше батч, тем стабильнее градиент. Глобальный батч при обучении больших моделей обычно составляет **миллионы токенов** — один GPU столько не вместит. Один из выходов — **накопление градиентов**: считаем по маленькой порции (микробатчу), складываем градиенты и обновляем параметры, когда накопилось достаточно:

```python
data = [(1.0, 2.1), (2.0, 3.9), (3.0, 6.2), (4.0, 7.8), (5.0, 10.1), (6.0, 12.2), (7.0, 13.8), (8.0, 16.1)]
w = 0.5

def grad(batch, w):                         # градиент среднеквадратичной ошибки mean((w·x - y)²) по w
    return sum(2 * (w * x - y) * x for x, y in batch) / len(batch)

full = grad(data, w)                        # весь батч сразу

micro = [data[i:i + 2] for i in range(0, len(data), 2)]   # 4 микробатча по 2 примера
acc = 0.0
for mb in micro:
    acc += grad(mb, w) / len(micro)         # накапливаем, деля на число шагов
print(f"весь батч: {full:.4f}, накопление: {acc:.4f}")
```

Результаты в точности совпадают. Накопление градиентов меняет **время** на **память**: несколько прямых и обратных проходов на одно обновление параметров.

## 3.4 Параллелизм по данным и all-reduce

**Параллелизм по данным** (Data Parallelism, DP) — самый распространённый: на каждом GPU лежит **полная копия модели**, каждый обрабатывает **свои данные** и считает свои градиенты; затем все GPU **усредняют** градиенты, и каждый обновляет параметры этим средним, так что копии остаются одинаковыми. Математически это то же накопление градиентов — просто микробатчи одновременно считаются на разных GPU.

Операция «каждый GPU получает сумму всех градиентов» называется **all-reduce**. Наивно можно отправить всё на один GPU, сложить и разослать обратно, но этот GPU станет узким местом. На практике часто используют **кольцевой all-reduce**: GPU выстраиваются в кольцо, и каждый общается только со следующим. Делим данные на n кусков:

1. **reduce-scatter**: n−1 раундов; в каждом каждый GPU передаёт следующему один кусок, а тот прибавляет его к своему. В конце у каждого GPU есть **один кусок** полной суммы.
2. **all-gather**: ещё n−1 раундов разносят эти готовые куски по всему кольцу.

```python
def ring_allreduce(data):
    n = len(data)                              # число GPU
    c = len(data[0]) // n                      # длина куска
    buf = [list(d) for d in data]
    sent = [0] * n                             # сколько чисел отправил каждый GPU
    for step in range(n - 1):                  # ① reduce-scatter
        msgs = []
        for i in range(n):
            k = (i - step) % n                 # на этом шаге GPU i отправляет кусок k
            msgs.append(((i + 1) % n, k, buf[i][k * c:(k + 1) * c]))
            sent[i] += c
        for dst, k, chunk in msgs:
            for j in range(c):
                buf[dst][k * c + j] += chunk[j]
    for step in range(n - 1):                  # ② all-gather
        msgs = []
        for i in range(n):
            k = (i + 1 - step) % n
            msgs.append(((i + 1) % n, k, buf[i][k * c:(k + 1) * c]))
            sent[i] += c
        for dst, k, chunk in msgs:
            buf[dst][k * c:(k + 1) * c] = chunk
    return buf, sent

grads = [[1, 2, 3, 4], [10, 20, 30, 40], [100, 200, 300, 400], [1000, 2000, 3000, 4000]]
result, sent = ring_allreduce(grads)
for i, r in enumerate(result):
    print(f"GPU {i}: {r}")
print("отправлено каждым GPU:", sent, "(в градиенте всего 4 числа)")
```

Каждый GPU отправляет лишь `2(n−1)/n` объёма градиента — даже при 1000 GPU меньше двух градиентов, — и все связи работают одновременно. Библиотека NVIDIA **NCCL** реализует такие «коллективные» операции, и `DistributedDataParallel` (DDP) в PyTorch использует её для синхронизации градиентов.

## 3.5 ZeRO и FSDP: убираем избыточность

У параллелизма по данным есть расточительность: каждый GPU хранит **полную** копию параметров, градиентов и состояния оптимизатора (16 байт на параметр). **ZeRO** от Microsoft (2019) заметил: раз все хранят одно и то же, это можно **разрезать и хранить вскладчину**, подгружая куски только по мере надобности:

| Стадия | Что разделяется | Память на GPU (N параметров, n GPU) |
|--------|-----------------|-------------------------------------|
| обычный DP | ничего | 16N |
| ZeRO-1 | состояние оптимизатора (12 байт) | 4N + 12N / n |
| ZeRO-2 | плюс градиенты | 2N + 14N / n |
| ZeRO-3 | плюс сами параметры | 16N / n |

```python
def zero_gb(N, n, stage):
    per_param = {0: 16, 1: 4 + 12 / n, 2: 2 + 14 / n, 3: 16 / n}[stage]
    return N * per_param / 1e9

N, n = 70e9, 64
for stage in range(4):
    print(f"ZeRO-{stage}: {zero_gb(N, n, stage):7.1f} ГБ на GPU")
```

При ZeRO-3 каждый GPU хранит лишь 1/n параметров; перед вычислением слоя он собирает параметры этого слоя с остальных GPU (all-gather) и после использования выбрасывает. Встроенный в PyTorch **FSDP** (Fully Sharded Data Parallel) — это реализация ZeRO-3, а библиотека DeepSpeed предоставляет ZeRO целиком.

## 3.6 Тензорный и конвейерный параллелизм

Когда матрицы одного слоя слишком велики или хочется уменьшить вычисления на каждом GPU, приходится делить **саму модель**.

**Тензорный параллелизм** (Tensor Parallelism, TP, из Megatron-LM от NVIDIA) делит одно матричное умножение между несколькими GPU. В MLP первая матрица режется **по столбцам**, а вторая — **по строкам**; каждый GPU независимо считает свою часть, и в конце достаточно одного all-reduce, чтобы сложить результаты:

```python
def matmul(A, B):
    return [[sum(a * b for a, b in zip(row, col)) for col in zip(*B)] for row in A]

def relu(M):
    return [[max(0, v) for v in row] for row in M]

x = [[1, 2], [3, -4]]                       # 2 токена по 2 измерения
W = [[1, 0, 2, -1], [0, 1, 1, 3]]           # 2 → 4 (первый слой MLP)
V = [[1, 2], [0, 1], [1, 0], [2, 1]]        # 4 → 2 (второй слой MLP)
full = matmul(relu(matmul(x, W)), V)        # всё вычисление на одном GPU

W0, W1 = [r[:2] for r in W], [r[2:] for r in W]   # GPU 0 берёт первые два столбца, GPU 1 — последние два
V0, V1 = V[:2], V[2:]                              # и V соответственно режется по строкам
part0 = matmul(relu(matmul(x, W0)), V0)            # каждый GPU считает свою часть без обмена посередине
part1 = matmul(relu(matmul(x, W1)), V1)
summed = [[a + b for a, b in zip(r0, r1)] for r0, r1 in zip(part0, part1)]   # один all-reduce
print("целиком:           ", full)
print("тензорный параллел.:", summed, "совпадает" if full == summed else "различается")
```

(ReLU применяется поэлементно, поэтому применять её к каждому куску столбцов отдельно совершенно правильно. Внимание можно делить по головам.) Тензорный параллелизм обменивается данными на каждом слое и требует очень быстрых связей между GPU, поэтому его обычно используют только среди 8 GPU **внутри одной машины** (соединённых NVLink).

**Конвейерный параллелизм** (Pipeline Parallelism, PP) делит модель **по слоям** — скажем, 80 слоёв на 8 GPU по 10, — и данные проходят через них, как по конвейеру. Проблема: когда GPU 1 закончил первый батч, GPU 8 только начинает; остальные ждут, и это простаивание называется **пузырём** (bubble). Решение — разбить батч на много микробатчей, которые идут друг за другом:

```python
def bubble(p, m):              # p ступеней конвейера, m микробатчей
    return (p - 1) / (m + p - 1)

for m in (1, 4, 16, 64):
    print(f"конвейер из 8 ступеней, {m:>2} микробатчей: GPU простаивают {bubble(8, m):.0%} времени")
```

## 3.7 Повторное вычисление активаций и всё вместе

- **Повторное вычисление активаций** (activation checkpointing): вместо того чтобы хранить все промежуточные результаты прямого прохода, сохраняют лишь несколько «контрольных точек», а остальное **пересчитывают** из них, когда это понадобится обратному проходу. Примерно на треть больше вычислений — и большая экономия памяти.
- **Всё вместе**: настоящее большое обучение использует сразу несколько видов параллелизма. Обучая Llama 3 405B на 16 000 H100, Meta сочетала тензорный параллелизм (8 GPU внутри машины), конвейерный (16 ступеней), параллелизм по данным (FSDP) и, для длинных последовательностей, **контекстный параллелизм** (одна длинная последовательность делится между GPU) — «4D-параллелизм». Модели со смесью экспертов (урок 4) добавляют **экспертный параллелизм**: разные эксперты живут на разных GPU.
- **Сбои**: когда десятки тысяч GPU работают месяцами, аппаратные сбои — обычное дело. В статье о Llama 3 сообщается о более чем 400 неожиданных прерываниях за 54 дня. Поэтому при обучении часто сохраняют **контрольные точки** (checkpoints) и после сбоя продолжают с последней.

## 3.8 Итоги

- FP32 / FP16 / BF16 / FP8: меньше битов — быстрее и экономнее, ценой точности и диапазона; у BF16 диапазон как у FP32, это нынешний стандарт.
- Смешанная точность: матричные операции в BF16, обновления над главными весами в FP32 (мелкие обновления в BF16 теряются); FP16 требует масштабирования потерь.
- Накопление градиентов: складываем градиенты нескольких микробатчей перед обновлением — время в обмен на память.
- Параллелизм по данным: полная модель на каждом GPU, разные данные, усреднение градиентов через all-reduce; в кольцевом all-reduce каждый GPU отправляет лишь 2(n−1)/n объёма данных.
- ZeRO / FSDP: распределяют состояние оптимизатора, градиенты и параметры по GPU; при ZeRO-3 у каждого 1/n.
- Тензорный параллелизм режет матрицы слоя по строкам и столбцам, требует много обмена и используется внутри машины; конвейерный режет по слоям, а микробатчи уменьшают пузырь.
- Повторное вычисление активаций меняет вычисления на память; большое обучение сочетает несколько видов параллелизма и часто сохраняет контрольные точки.

### Задание 5: Почему BF16?

Какова главная причина, по которой BF16 вытеснил FP16 при обучении больших моделей?

- BF16 точнее FP16
- у BF16 столько же битов порядка, сколько у FP32, а значит тот же диапазон: он редко переполняется или обнуляется, и масштабирование потерь не нужно
- BF16 занимает всего 8 битов
- BF16 не нужны главные веса в FP32

<details>
<summary>Ответ и разбор</summary>

У BF16 8 битов порядка и диапазон FP32; у FP16 их всего 5, максимум 65504, а очень маленькие градиенты обращаются в 0. Точность BF16 на самом деле **ниже**, чем у FP16 (7 битов мантиссы против 10), поэтому обновления по-прежнему делают над главными весами в FP32.
</details>

### Задание 6: Что делит ZeRO-3

Что ZeRO-3 (или FSDP) дополнительно разделяет поверх параллелизма по данным?

- только данные
- только состояние оптимизатора
- состояние оптимизатора, градиенты и параметры — по всем GPU
- слои модели — по разным GPU

<details>
<summary>Ответ и разбор</summary>

ZeRO-1 разделяет состояние оптимизатора, ZeRO-2 добавляет градиенты, а ZeRO-3 — ещё и параметры, так что каждый GPU хранит 1/n и собирает нужное на лету. Разделение по слоям — это конвейерный параллелизм.
</details>
