Вы обучили модель — как понять, хороша ли она? Насколько лучше прошлой версии? Чужих моделей? Это гораздо сложнее, чем кажется: языковые модели умеют так много, что любой отдельный балл показывает лишь одну сторону. Этот урок о распространённых методах оценки и о ловушках при чтении результатов.

## 5.1 Само языковое моделирование: перплексия и биты на байт

Самая прямая мера — **потери** модели на невиданном тексте (средняя отрицательная логвероятность на токен) или их экспонента — **перплексия** (perplexity, урок 1 части 3):

```python
import math

probs = [0.25, 0.6, 0.05, 0.9, 0.4]               # вероятность, которую модель дала каждому истинному токену
nll = [-math.log(p) for p in probs]               # отрицательная логвероятность каждого токена (в натах)
loss = sum(nll) / len(nll)
print(f"средние потери {loss:.3f} нат/токен, перплексия {math.exp(loss):.2f}")

text = "Чудно!"                                   # пусть эти 5 токенов складываются в такой текст
n_bytes = len(text.encode("utf-8"))
bpb = sum(nll) / math.log(2) / n_bytes            # общее количество информации в битах, делённое на байты
print(f"{n_bytes} байт, {bpb:.3f} бита на байт")
```

У перплексии есть проблема: она зависит от **токенизатора**. С более крупными токенами (больше текста на токен) каждый токен труднее предсказать, и перплексия выше, хотя модель ничуть не хуже. Поэтому для сравнения моделей с разными токенизаторами часто используют **биты на байт** (bits per byte, BPB): общее количество информации переводят в биты и делят на число байтов исходного текста — это уже не зависит от токенизации.

Потери — главная метрика во время обучения: гладкая, стабильная и напрямую связанная с законами масштабирования (урок 2). Но пользователей волнует, правильно ли модель отвечает на вопросы, пишет ли работающий код, выполняет ли инструкции, — а для этого нужны специальные тестовые наборы.

## 5.2 Тесты с выбором ответа: даже оценивать надо аккуратно

**MMLU** (2020) — самый известный тест с выбором ответа: около 14 000 вопросов с четырьмя вариантами по 57 предметам (математика, история, право, медицина…). Его преемник **MMLU-Pro** (2024) содержит десять вариантов и больше задач на рассуждение; **GPQA** (2023) — вопросы по физике, химии и биологии уровня аспирантуры, составленные так, что даже поиск в интернете почти не помогает («GPQA Diamond» — его 198 самых трудных вопросов).

Оценивать модель на тестах с выбором ответа можно двумя способами:

1. **Генерация ответа**: перечислить варианты в промпте, дать модели вывести «A», «B»… и проверить вывод. Подходит для чат-моделей.
2. **Сравнение вероятностей**: приписать текст каждого варианта к вопросу, вычислить **логвероятность**, которую модель даёт этому тексту, и выбрать наибольшую. Модели не нужно соблюдать формат ответа, поэтому так оценивают базовые модели, ещё не прошедшие обучение инструкциям.

У второго способа есть ловушка: в длинных вариантах больше токенов, и их суммарная логвероятность ниже. Поэтому её часто **усредняют** по длине — а это порой, наоборот, благоприятствует длинным вариантам:

```python
# логвероятности токенов каждого варианта (варианты разной длины)
options = {
    "A": [-1.2, -0.8, -0.9],
    "B": [-2.5],
    "C": [-1.0, -1.1],
    "D": [-3.0, -0.2, -0.3, -0.4],
}
by_sum = max(options, key=lambda k: sum(options[k]))
by_mean = max(options, key=lambda k: sum(options[k]) / len(options[k]))
for k, lp in options.items():
    print(f"{k}: токенов {len(lp)}, сумма {sum(lp):5.2f}, среднее {sum(lp) / len(lp):6.3f}")
print("выбор по сумме:", by_sum, "; выбор по среднему:", by_mean)
```

Та же модель, тот же вопрос, другой способ оценки — другой ответ. Поэтому **при сравнении результатов все детали оценки должны совпадать**: тот же формат промпта, то же число примеров (0-shot или 5-shot), тот же способ подсчёта. Вот почему «балл MMLU» одной и той же модели в разных статьях часто различается на несколько пунктов.

## 5.3 Задачи на генерацию: математика и код

### Математика: точное совпадение

Наборы вроде **GSM8K** (текстовые задачи начальной школы), **MATH** (олимпиадная математика) и **AIME** (американская пригласительная математическая олимпиада, 30 задач в год; с 2024 года широко используется для моделей-рассуждателей) дают модели расписать решение, затем извлекают ответ и сравнивают с эталоном. «Извлечь» звучит просто, но легко ошибиться: модель может написать `1,000`, `1000.0`, `$1000` или `ответ: 1000 долларов`… Обычно ответы перед сравнением **нормализуют** или просят модель писать итоговый ответ в фиксированном формате (например, `\boxed{1000}`).

### Код: pass@k

Наборы вроде **HumanEval** (OpenAI, 2021, 164 задачи на функции Python) и MBPP запускают код модели в песочнице и проверяют его модульными тестами. Обычная метрика — **pass@k**: модель генерирует k ответов на задачу, и задача считается решённой, если **хотя бы один** проходит тесты.

Как оценить pass@k? Прямой способ — действительно сгенерировать k ответов и посмотреть, есть ли верный, — очень шумный. Лучше сгенерировать на задачу n (n ≥ k) ответов, посчитать c верных и с помощью сочетаний найти вероятность того, что «среди k случайно выбранных из n есть хотя бы один верный»:

```formula
pass@k = 1 − C(n − c, k) / C(n, k)
```

```python
from math import comb

def pass_at_k(n, c, k):
    if n - c < k:                      # неверных меньше k: любые k выбранных содержат верный
        return 1.0
    return 1 - comb(n - c, k) / comb(n, k)

def naive(n, c, k):                    # частая ошибка: считать c/n вероятностью успеха каждой попытки
    return 1 - (1 - c / n) ** k

for n, c, k in [(10, 3, 1), (10, 3, 5), (200, 10, 10), (200, 10, 100)]:
    print(f"n={n:3d} c={c:2d} k={k:3d}: несмещённая {pass_at_k(n, c, k):.4f}, наивная {naive(n, c, k):.4f}")
```

`1 − (1 − c/n)^k` выглядит разумно, но предполагает выбор «с возвращением» и систематически **занижает** pass@k. Несмещённую оценку выше предложили авторы HumanEval.

Тесты по коду всё ближе к настоящей работе: **LiveCodeBench** постоянно собирает свежие олимпиадные задачи, чтобы они не успели «загрязнить» обучающие данные; **SWE-bench Verified** (2024) — 500 задач из настоящих проектов на GitHub, где модель должна прочитать всю кодовую базу и изменить код так, чтобы прошли существующие тесты проекта, — это уже оценка **агентов** (часть 7).

## 5.4 Предпочтения людей: арена и Эло

У многих качеств — помогает ли ответ, хорошо ли написан текст, подходящий ли тон — нет эталонного ответа. **Chatbot Arena** (LMArena, с 2023 года) устроена так: пользователь задаёт вопрос, две анонимные модели отвечают, и пользователь голосует за лучший ответ. Миллионы голосов выстраивают рейтинг всех моделей.

Рейтинг считается по системе **Эло** из шахмат (и более строгой модели Брэдли — Терри): разница рейтингов задаёт «ожидаемый результат», и результат лучше ожидаемого добавляет очки, а хуже — отнимает:

```formula
ожидаемый результат E_A = 1 / (1 + 10^((R_B − R_A) / 400))　　новый рейтинг R_A' = R_A + K · (фактический результат − E_A)
```

```python
def elo(ra, rb, score_a, k=32):          # score_a: 1 — A выиграла, 0.5 — ничья, 0 — проиграла
    expected_a = 1 / (1 + 10 ** ((rb - ra) / 400))
    change = k * (score_a - expected_a)
    return ra + change, rb - change

print("две модели по 1500, A выиграла:", elo(1500, 1500, 1))
print("A (1600) проиграла B (1400):", [round(v, 1) for v in elo(1600, 1400, 0)])
print("A (1600) обыграла B (1400):", [round(v, 1) for v in elo(1600, 1400, 1)])
print("ожидаемая доля побед при разнице 400 очков:", round(1 / (1 + 10 ** (-400 / 400)), 3))
```

Сенсация (сильный проигрывает слабому) сильно меняет рейтинги, ожидаемый исход — слабо.

### LLM в роли судьи

Голоса людей медленные и дорогие, поэтому судьёй часто делают сильную модель (**LLM-as-a-judge**), как в MT-Bench и AlpacaEval. Это удобно, но у таких судей есть известные предвзятости:

- **позиционная**: предпочтение ответа, показанного первым (или последним). Средство: оценить ещё раз, поменяв порядок, и принимать только совпадающие вердикты.
- **по длине**: предпочтение более длинных и подробных ответов, даже если они не лучше. Поэтому в AlpacaEval 2.0 появился «контролирующий длину» процент побед.
- **самопредпочтение**: предпочтение ответов, написанных самим судьёй (или моделью его семейства).
- и судьи тоже ошибаются: в специальных вопросах они могут разбираться не лучше оцениваемых моделей.

## 5.6 Ловушки при чтении результатов

- **Утечка (контаминация)**: если тестовые вопросы есть в обучающих данных, баллы завышены (деконтаминацию мы разбирали в уроке 1). Новые тесты (LiveCodeBench, ежегодный AIME) отчасти избегают этого.
- **Чувствительность к промпту**: другая формулировка, другие примеры или перемешанные варианты ответа могут сдвинуть балл на несколько пунктов.
- **Закон Гудхарта**: «когда мера становится целью, она перестаёт быть хорошей мерой». Оптимизация под конкретный рейтинг может сделать модель хорошей именно на этом тесте, ничего не улучшив в остальном.
- **Статистический шум**: тестовый набор конечен, так что у самого балла есть случайная ошибка. При точности p на n вопросах 95-процентный доверительный интервал примерно равен `p ± 1.96 × √(p(1 − p) / n)`:

```python
import math

def accuracy_ci(correct, total):
    p = correct / total
    half = 1.96 * math.sqrt(p * (1 - p) / total)
    return p, p - half, p + half

for name, correct in [("модель A", 360), ("модель B", 375)]:
    p, low, high = accuracy_ci(correct, 500)
    print(f"{name}: верно {correct} из 500, точность {p:.1%}, 95% доверительный интервал [{low:.1%}, {high:.1%}]")
```

72% и 75% выглядят как разница в 3 пункта, но интервалы сильно перекрываются — при всего 500 вопросах разница **вполне может быть везением**. Особенно осторожными будьте с тестами из малого числа задач (в AIME всего 30 задач в год!): обычно каждую задачу решают по нескольку раз и сообщают среднюю точность.

### Лучшая оценка — ваша собственная

Публичные тесты измеряют общие способности. Если модель нужна для конкретной работы — сортировки писем в поддержку, извлечения пунктов из договоров, ответов о продуктах вашей компании, — надёжнее всего **собрать несколько десятков или сотен настоящих примеров**, написать эталонные ответы или правила оценки и сделать собственный тестовый набор. Прогоняйте его при каждой смене модели или правке промпта. Подробнее об этом — в части 7.

## 5.7 Итоги

- Перплексия (или потери) измеряет языковое моделирование, но зависит от токенизатора; биты на байт — нет.
- Тесты с выбором ответа оценивают генерацией ответа или сравнением логвероятностей вариантов; способ подсчёта, формат промпта и число примеров влияют на баллы и должны совпадать при сравнении.
- Математика — точное совпадение после нормализации ответов; код — модульные тесты и pass@k с несмещённой оценкой `1 − C(n−c, k)/C(n, k)`.
- Когда эталона нет — предпочтения людей (арена + Эло) или LLM-судьи с их позиционной предвзятостью, предвзятостью по длине и самопредпочтением.
- Тесты насыщаются, загрязняются и чувствительны к промпту; у баллов есть статистическая ошибка — смотрите на доверительные интервалы.
- Сделайте собственный тестовый набор под свою задачу.
