训练完一个模型，怎么知道它好不好？比上一个版本强多少？比别家的模型呢？这比想象的难得多：语言模型能做的事情太多了，任何一个分数都只反映了一个侧面。这一课介绍常用的评测方法，以及解读分数时要注意的陷阱。

## 5.1 语言建模本身：困惑度和每字节比特数

最直接的指标是模型在没见过的文本上的**损失**（平均每个 token 的负对数概率），或者它的指数——**困惑度**（perplexity，第三部分第 1 课）：

```python
import math

probs = [0.25, 0.6, 0.05, 0.9, 0.4]               # 模型给真实的下一个 token 的概率
nll = [-math.log(p) for p in probs]               # 每个 token 的负对数概率（单位：nat）
loss = sum(nll) / len(nll)
print(f"平均损失 {loss:.3f} nat/token，困惑度 {math.exp(loss):.2f}")

text = "今天天气很好"                                # 假设这 5 个 token 拼起来是这段文字
n_bytes = len(text.encode("utf-8"))
bpb = sum(nll) / math.log(2) / n_bytes            # 总信息量换算成比特，再除以字节数
print(f"{n_bytes} 个字节，每字节 {bpb:.3f} 比特")
```

困惑度有一个问题：它依赖于**分词器**。分词器切得粗（一个 token 包含的文字多），每个 token 就更难预测，困惑度更高，但这并不说明模型更差。所以比较不同分词器的模型时，常用**每字节比特数**（bits per byte, BPB）：把总的信息量换算成比特，除以原文的字节数，就和分词方式无关了。

损失是训练时最重要的指标——它平滑、稳定，和规模定律直接相关（第 2 课）。但用户关心的是「能不能答对题、写对代码、听懂指令」，这需要专门的评测集。

## 5.2 选择题：怎么打分也有讲究

**MMLU**（2020）是最有名的选择题评测：57 个学科（数学、历史、法律、医学……）的约 1.4 万道四选一题目。它的升级版 **MMLU-Pro**（2024）有十个选项、更多推理题；**GPQA**（2023）是研究生水平的物理、化学、生物题，题目设计得连上网搜索也很难找到答案（「GPQA Diamond」是其中最难的 198 道）。

让模型做选择题，有两种打分方式：

1. **生成答案**：在提示里列出选项，让模型输出「A」「B」……，再检查输出。适合对话模型。
2. **比较概率**：把每个选项的文字接在题目后面，计算模型给这段文字的**对数概率**，选概率最高的。不需要模型会按格式回答，适合还没经过指令微调的基础模型。

第二种方式有个陷阱：选项越长，包含的 token 越多，对数概率加起来就越低。所以常常要按长度**取平均**——但这样做有时又会反过来偏爱长选项：

```python
# 每个选项各个 token 的对数概率（选项长短不一）
options = {
    "A": [-1.2, -0.8, -0.9],
    "B": [-2.5],
    "C": [-1.0, -1.1],
    "D": [-3.0, -0.2, -0.3, -0.4],
}
by_sum = max(options, key=lambda k: sum(options[k]))
by_mean = max(options, key=lambda k: sum(options[k]) / len(options[k]))
for k, lp in options.items():
    print(f"{k}：{len(lp)} 个 token，总和 {sum(lp):5.2f}，平均 {sum(lp) / len(lp):6.3f}")
print("按总和选：", by_sum, "；按平均选：", by_mean)
```

同一个模型、同一道题，换一种打分方式，选出的答案就不一样了。所以**比较分数时，评测的细节必须完全相同**：同样的提示格式、同样的示例数量（0-shot 还是 5-shot）、同样的打分方式。不同论文里同一个模型的「MMLU 分数」常常相差好几分，原因就在这里。

## 5.3 生成题：数学和代码

### 数学：精确匹配

**GSM8K**（小学数学应用题）、**MATH**（竞赛数学）、**AIME**（美国数学邀请赛，每年 30 道题，2024 年起被广泛用来评测推理模型）这类评测，让模型写出解题过程，最后提取答案和标准答案比较。「提取」看似简单，其实很容易出错：模型可能写 `1,000`、`1000.0`、`$1000`、`答案是 1000 元`……通常要先**规范化**再比较，或者要求模型把最终答案写在固定的格式里（比如 `\boxed{1000}`）。

### 代码：pass@k

**HumanEval**（OpenAI，2021，164 道 Python 函数题）、MBPP 这类评测，把模型写的代码放进沙箱运行，用单元测试判断对错。常用的指标是 **pass@k**：让模型对每道题生成 k 个答案，**只要有一个**通过测试就算解出。

怎样估计 pass@k？最直接的方法是真的生成 k 个答案看有没有对的，但这样随机性很大。更好的做法是对每道题生成 n 个（n ≥ k）答案，数出其中 c 个是对的，再用组合数算出「从 n 个里随机选 k 个，至少有一个对」的概率：

```formula
pass@k = 1 − C(n − c, k) / C(n, k)
```

```python
from math import comb

def pass_at_k(n, c, k):
    if n - c < k:                      # 错的不够 k 个：随便选 k 个都至少有一个对的
        return 1.0
    return 1 - comb(n - c, k) / comb(n, k)

def naive(n, c, k):                    # 一个常见的错误做法：把 c/n 当作每次的成功率
    return 1 - (1 - c / n) ** k

for n, c, k in [(10, 3, 1), (10, 3, 5), (200, 10, 10), (200, 10, 100)]:
    print(f"n={n:3d} c={c:2d} k={k:3d}：无偏估计 {pass_at_k(n, c, k):.4f}，错误做法 {naive(n, c, k):.4f}")
```

`1 − (1 − c/n)^k` 看起来合理，但它假设可以「有放回地」抽取，会系统性地**低估** pass@k。HumanEval 的论文给出了上面的无偏估计。

现在的代码评测越来越接近真实工作：**LiveCodeBench** 不断收集新发布的竞赛题，避免题目被训练数据「污染」；**SWE-bench Verified**（2024）是 500 个来自真实 GitHub 项目的问题，模型要阅读整个代码库、修改代码，让项目原有的测试通过——这已经是在评测**智能体**（第七部分）的能力了。

## 5.4 人类偏好：竞技场和 Elo

很多能力——回答是否有帮助、写作好不好、语气是否合适——没有标准答案。**Chatbot Arena**（LMArena，2023 年起）的做法是：用户输入一个问题，两个匿名模型各给一个回答，用户投票选择更好的那个。用几百万次投票，就能给所有模型排出名次。

排名用的是国际象棋里的 **Elo 评分**（以及更严格的 Bradley–Terry 模型）：两个模型的分差决定了「预期胜率」，实际结果比预期好就加分，比预期差就减分：

```formula
预期得分 E_A = 1 / (1 + 10^((R_B − R_A) / 400))　　新分数 R_A' = R_A + K · (实际得分 − E_A)
```

```python
def elo(ra, rb, score_a, k=32):          # score_a：A 赢 1，平局 0.5，输 0
    expected_a = 1 / (1 + 10 ** ((rb - ra) / 400))
    change = k * (score_a - expected_a)
    return ra + change, rb - change

print("两个 1500 分的模型，A 赢：", elo(1500, 1500, 1))
print("1600 分的 A 输给 1400 分的 B：", [round(v, 1) for v in elo(1600, 1400, 0)])
print("1600 分的 A 赢了 1400 分的 B：", [round(v, 1) for v in elo(1600, 1400, 1)])
print("400 分的差距意味着预期胜率：", round(1 / (1 + 10 ** (-400 / 400)), 3))
```

爆冷（强者输给弱者）带来大幅的分数变化，意料之中的结果只带来小幅变化。

### 大模型当评委

人工投票又慢又贵，于是常常让一个强大的模型来当评委（**LLM-as-a-judge**），比如 MT-Bench、AlpacaEval。它很方便，但有几种已知的偏差：

- **位置偏差**：倾向于选择先出现（或后出现）的回答。对策：交换顺序再评一次，两次结果一致才算数。
- **长度偏差**：倾向于更长、更详细的回答，哪怕内容并不更好。AlpacaEval 2.0 因此推出了「长度控制」的胜率。
- **自我偏好**：倾向于自己（或同一家族的模型）写的回答。
- 而且评委本身也会犯错，在专业问题上未必比被评测的模型更懂。

## 5.5 2026 年常见的评测

| 方向 | 代表性评测 |
|------|------------|
| 知识与推理 | MMLU-Pro、GPQA Diamond、**HLE**（Humanity's Last Exam，2025，约 2500 道各领域专家出的难题） |
| 数学 | MATH-500、AIME 2024/2025 |
| 代码 | LiveCodeBench、SWE-bench Verified |
| 指令遵循 | **IFEval**（「用不超过 100 个词」「不要用逗号」等可以自动检查的指令） |
| 长上下文 | 大海捞针（needle in a haystack）、RULER |
| 智能体 | SWE-bench、τ-bench（客服场景中调用工具）、浏览网页、操作电脑的评测 |
| 抽象推理 | ARC-AGI（用图形谜题考察「学习新规则」的能力） |
| 人类偏好 | LMArena |
| 安全 | 拒答有害请求、越狱攻击、偏见等专门的评测 |

评测集的「寿命」越来越短：MMLU 发布时最好的模型只有 40 多分，几年后前沿模型都在 90 分上下，**饱和**了，区分不出高低；GSM8K 也是如此。于是不断有更难的评测出现，HLE 的名字（「人类的最后一场考试」）就反映了这种追赶。

## 5.6 解读分数的陷阱

- **数据污染**：评测题如果出现在训练数据里，分数就虚高了（第 1 课讲过去污染）。新出的评测（比如 LiveCodeBench、每年的 AIME）可以一定程度上避免这个问题。
- **提示敏感**：换一种提示的措辞、换几个示例、换一下选项顺序，分数可能变化好几分。
- **古德哈特定律**：「当一个指标变成目标，它就不再是一个好的指标。」专门为了刷某个排行榜而优化，可能让模型在这个评测上很好，在别的地方却没有提升。
- **统计噪声**：评测集是有限的，分数本身有随机误差。正确率 p、题目数 n 时，95% 置信区间大约是 `p ± 1.96 × √(p(1 − p) / n)`：

```python
import math

def accuracy_ci(correct, total):
    p = correct / total
    half = 1.96 * math.sqrt(p * (1 - p) / total)
    return p, p - half, p + half

for name, correct in [("模型 A", 360), ("模型 B", 375)]:
    p, low, high = accuracy_ci(correct, 500)
    print(f"{name}：500 题对了 {correct} 题，正确率 {p:.1%}，95% 置信区间 [{low:.1%}, {high:.1%}]")
```

72% 和 75% 看起来差了 3 分，但两个区间大幅重叠——只有 500 道题时，这点差距**完全可能是运气**。题目少的评测（AIME 每年只有 30 道题！）尤其要注意：常见的做法是对每道题采样多次，报告平均的正确率。

### 最好的评测是你自己的评测

公开评测衡量的是通用能力。如果你要用模型做一件具体的事——给客服邮件分类、从合同里提取条款、回答你公司产品的问题——最可靠的办法是**收集几十到几百个真实的例子**，写好标准答案或评分规则，建一个自己的评测集。每次换模型、改提示词，都先在它上面跑一遍。第七部分会更详细地讲。

## 5.7 小结

- 困惑度（或损失）衡量语言建模能力，但依赖分词器；每字节比特数与分词无关。
- 选择题可以生成答案，也可以比较选项的对数概率；打分方式、提示格式、示例数量都会影响分数，比较时必须一致。
- 数学题用精确匹配，要先规范化答案；代码题用单元测试和 pass@k，pass@k 要用无偏估计 `1 − C(n−c, k)/C(n, k)`。
- 没有标准答案时用人类偏好（Arena + Elo）或大模型评委；评委有位置、长度、自我偏好等偏差。
- 评测会饱和、会被污染、对提示敏感；分数有统计误差，要看置信区间。
- 为自己的任务建立专门的评测集。

### 练习 1：困惑度

输入一行数，是模型给每个真实 token 的概率。输出平均损失（nat）和困惑度，各保留 3 位小数，用空格隔开。

```text
样例输入：0.25 0.6 0.05 0.9 0.4
样例输出：1.183 3.264
```

<details>
<summary>提示</summary>

损失 = `-sum(math.log(p) for p in probs) / len(probs)`，困惑度 = `math.exp(损失)`。
</details>

<!-- exercise: pass-at-k -->
### 练习 2：pass@k

输入 n、c、k：每道题生成了 n 个答案，其中 c 个通过了测试。用无偏估计计算 pass@k，保留 4 位小数。

```text
样例输入：10 3 5
样例输出：0.9167
```

<details>
<summary>提示</summary>

`from math import comb`；当 `n - c < k` 时结果是 1，否则是 `1 - comb(n - c, k) / comb(n, k)`。
</details>

<!-- exercise: elo -->
### 练习 3：Elo 评分

输入一行：A 的分数、B 的分数、A 的比赛结果（1 赢、0.5 平、0 输）、K 值。输出比赛后 A 和 B 的新分数，各保留 1 位小数，用空格隔开。

```text
样例输入：1600 1400 0 32
样例输出：1575.7 1424.3
```

<details>
<summary>提示</summary>

`expected_a = 1 / (1 + 10 ** ((rb - ra) / 400))`，`change = k * (score - expected_a)`，A 加上 change，B 减去 change。
</details>

<!-- exercise: accuracy-ci -->
### 练习 4：正确率的置信区间

输入答对的题数和总题数，输出正确率以及 95% 置信区间的下限和上限（用 `p ± 1.96 × √(p(1 − p)/n)`），都保留 3 位小数，用空格隔开。

```text
样例输入：360 500
样例输出：0.720 0.681 0.759
```

<details>
<summary>提示</summary>

`p = correct / total`，`half = 1.96 * math.sqrt(p * (1 - p) / total)`，输出 `p`、`p - half`、`p + half`。
</details>

<!-- exercise: small-diff -->
### 练习 5：差 3 分说明什么？

在一个有 200 道题的评测上，模型 X 的正确率是 70%，模型 Y 是 73%。下面哪个结论最合理？

- Y 一定比 X 强
- X 一定比 Y 强
- 这点差距在统计误差范围内，还不能确定谁更强，需要更多的题目或更多次的采样
- 评测集太小，分数毫无意义

<details>
<summary>答案与解析</summary>

200 道题、70% 左右的正确率，95% 置信区间的半宽约为 6.4 个百分点，两个模型的区间大幅重叠，3 分的差距很可能只是随机波动。分数并非毫无意义，只是不足以区分这两个模型。
</details>

<!-- exercise: judge-bias -->
### 练习 6：大模型评委

让一个大模型比较两个回答哪个更好时，下面哪种做法能减轻它的**位置偏差**？

- 只给它看更长的那个回答
- 交换两个回答的顺序再评一次，两次结论一致才采用
- 让被评测的模型自己当评委
- 把温度设为 2

<details>
<summary>答案与解析</summary>

位置偏差是指评委偏爱某个位置上的回答。交换顺序各评一次，就能发现并抵消这种偏差。让模型给自己打分会引入自我偏好；温度和回答长度与位置偏差无关。
</details>
